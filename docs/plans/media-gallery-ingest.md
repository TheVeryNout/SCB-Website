# Media Gallery Ingest And Publication Plan

## Purpose

This document is the reviewable implementation plan for restoring historical photo galleries and creating future galleries without allowing original JPEG uploads to bloat Git history.

It records:

- the verified current state
- user decisions and operating constraints
- faults found during the media-page discussion
- the selected architecture
- phased implementation and validation gates
- alternatives considered and rejected or deferred
- remaining questions that must not be resolved silently

This is an operational follow-up plan. It does not reopen the historical website implementation phases.

1. New full-resolution JPEG inputs do not need a retained original archive after successful conversion and validation.
2. A two-step conversion and CMS workflow is acceptable for the first implementation.

4. The confirmed YouTube source for the media page remains the `SkateClub Biriciana` playlist recorded in `public-data-register.md`.
5. Goodies 4 Tricks 2025 must publish all `14` Wix gallery images in the verified source order.

- Goodies 4 Tricks 2025 is explicitly locked to the complete 14-image source gallery

- any intentional omission must be visible in the review and recorded as an editorial decision

## Verified Current State

### Browser delivery

`PostGallery.astro` already provides strong delivery behavior:

- responsive gallery thumbnails are generated by Astro
- large lightbox images are explicitly converted to WebP
- large-view width is bounded to at most `2000px`
- large-view WebP quality is `86`
- PhotoSwipe provides progressive enhancement, keyboard navigation, captions, zoom, and direct-image fallback

This protects visitor performance, but it does not control what binary enters Git.

### Repository ingestion

The current Decap image widget stores selected uploads directly under:

- `src/assets/images/uploads/`

There is no configured pre-commit conversion step. A JPEG uploaded through the default path is committed as a JPEG before Astro transforms it.

Current tracked image blobs under `src/assets/images/` were measured at approximately:

- `56.69 MiB` total
- `48.03 MiB` `.jpg`
- `7.01 MiB` `.jpeg`
- `1.02 MiB` `.png`
- `0.63 MiB` `.webp`

The existing CMS upload folder itself was approximately `11 MiB` when audited. Build-time WebP generation does not reduce these source blobs or remove them from Git history.

### Gallery content ownership

The maintained content contract says the media collection controls public media entries shown on `/pics-n-vids/`.

Current behavior:

- `/pics-n-vids/` reads `getAllMedia()` only
- news posts independently own structured gallery items with `image`, required `alt`, and optional `caption`
- media entries currently own bare image paths without per-image alt text or captions
- the media page currently creates generic alternative text from title and position
- two standalone media galleries currently contain five images each
- several news posts have galleries but are not automatically represented on the media page

### Goodies 4 Tricks 2025

The source gallery has been individually verified:

- the rendered Wix gallery contains `14` images
- all `14` source image IDs exist in the retained local archive
- `13` were classified into `src/assets/images/wix-staging/posts/goodies-4-tricks-2025/`
- the remaining image was classified under `src/assets/images/wix-staging/homepage/site/` because it appeared in several captured sources
- no additional Wix scrape is required for this gallery
- the current Astro post publishes only `6` gallery entries and uses another source image as its cover

The six-image implementation is an incomplete editorial selection relative to the source gallery. It must not be treated as evidence that the source contained six images.

### Completeness outside Goodies 2025

The repository contains a substantial Wix reference pack and eight retained post HTML captures. That does not, by itself, prove every historical gallery was captured completely. Completeness must be audited per gallery, especially for lazy-loaded Wix media.

## Faults Found During Planning

The previous discussion exposed the following planning failures:

1. Current implementation state was incorrectly used as evidence of source completeness.
2. A post-specific staging count was treated as the full source count even though shared classification moved one gallery image elsewhere.
3. A proposal to put `showOnMediaPage` on posts would have shifted media-page ownership away from the existing media collection without first acknowledging that architectural change.
4. “Scraped,” “promoted into CMS uploads,” and “published in a gallery” were discussed as if they were the same state.
5. Build-time WebP delivery was initially conflated with pre-commit source conversion and therefore with Git-size control.
6. A possible editorial down-selection was introduced without first establishing whether the user wanted archive fidelity or highlights.

The implementation must keep these states explicit:

```text
captured source evidence
  -> completeness verified
  -> converted publication asset
  -> content metadata and ordering
  -> media-page inclusion
  -> generated responsive delivery assets
```

No step proves a later step happened.

## Selected Architecture

### 1. Media collection remains the explicit page index

The media page must continue to be driven by media entries. News posts must not appear merely because they happen to have a gallery.

A media photo-gallery entry will support one of two ownership modes:

#### Referenced post gallery

The media entry selects a canonical news post by stable slug. The post remains the sole owner of:

- gallery images
- image order
- alternative text
- captions

Conceptual content:

```yaml
title: "Goodies 4 Tricks 2025"
slug: "goodies-4-tricks-2025"
type: "photo-gallery"
postSlug: "goodies-4-tricks-2025"
summary: "..."
publishedAt: "..."
```

This avoids duplicating a fourteen-item gallery in both `posts` and `media`.

#### Standalone media gallery

A media entry with no owning post stores its own structured items:

```yaml
title: "Standalone gallery"
slug: "standalone-gallery"
type: "photo-gallery"
gallery:
  - image: "../../assets/images/uploads/example-01.webp"
    alt: "A skater performing a boardslide on the rail"
    caption: "Optional visible caption"
```

### 2. Validation rules

For `type: photo-gallery`:

- exactly one source must be present: `postSlug` or a local `gallery`
- `postSlug` must resolve to a public post with a non-empty gallery
- a standalone gallery must contain at least one structured gallery item
- every item requires non-empty alternative text
- captions remain optional
- duplicate media slugs remain invalid
- an unresolved post reference must fail validation/build

For `type: youtube`:

- the existing YouTube URL requirement remains

### 3. Shared presentation model

Page code should normalize referenced post galleries and standalone media galleries into one presentation model before rendering `PostGallery.astro`. The component must not need to know where a gallery is owned.

### 4. Asset policy

For new routine publication:

- JPEG/PNG inputs are temporary ingest material
- only validated WebP publication assets are added to `src/assets/images/uploads/`
- original inputs are not copied into Git or an external archive
- temporary ingest copies are discarded only after conversion and validation succeed
- the converter must never silently delete arbitrary user source paths
- source deletion outside the repository requires explicit authorization for that path at execution time

For retained Wix evidence:

- convert from the existing local evidence copy into a publication WebP
- do not create another JPEG copy under `uploads`
- do not delete the established raw evidence archive as part of gallery publication
- the user’s discard preference does not apply retroactively to the existing evidence archive; deleting that archive is outside this implementation

### 5. Historical fidelity policy

A historical gallery’s expected set and order must come from source evidence, not from the currently migrated subset.

Default:

- publish all verified source gallery images in source order
- use the same image as both cover and gallery item when that reflects the source and the cover is part of the source gallery
- draft descriptive alt text from visible content
- ask for user input only when identity, event meaning, or caption claims cannot be derived safely

## Converter Design

### Recommended implementation

Use the repository-owned two-step `bun run images:prepare` command backed by the declared `sharp@0.34.5` development dependency.

Why `sharp` is preferred:

- deterministic Node/Bun integration
- reliable EXIF orientation handling
- mature resize and WebP encoding
- suitable metadata inspection
- portable across development and automation environments supported by its binaries
- closely aligned with Astro’s existing image-processing ecosystem

The package-guard preflight was completed and the exact project-local dependency addition was explicitly approved before `sharp@0.34.5` was declared directly.

### Command contract

Implemented command:

```bash
bun run images:prepare -- \
  --input /path/to/input-folder \
  --output /path/to/review-folder \
  --slug goodies-4-tricks-2025
```

Optional flags lock or override `--max-edge` and `--quality`; `--help` documents the non-destructive contract.

Implemented behavior:

- accept JPEG, PNG, and WebP inputs
- inspect real file type rather than trusting the extension
- auto-orient from metadata
- preserve aspect ratio
- bound maximum dimensions according to the accepted benchmark
- encode WebP with an explicitly recorded quality setting
- strip unnecessary EXIF/location metadata
- use stable collision-safe filenames
- process files in deterministic input order
- never overwrite an existing output silently
- emit output atomically
- report input/output dimensions and byte sizes
- emit a machine-readable conversion manifest with hashes
- fail the batch clearly when any file is corrupt or unsupported
- leave the input untouched during conversion
- provide a review step before temporary originals are discarded

### Locked conversion settings

Selected defaults:

- longest edge: `2560px`
- source WebP quality: `88`
- WebP effort: `5`

The benchmark compared `2400px/85`, `2400px/88`, `2560px/88`, and `2560px/90` using:

- portrait phone photo
- landscape action photo
- detailed/high-motion skate image
- low-light image
- already-compressed JPEG
- transparent PNG if such uploads are allowed

Acceptance should consider:

- visible detail at normal and zoomed viewing sizes
- file-size reduction
- orientation correctness
- colour consistency
- absence of obvious blocking, smearing, or ringing
- sufficient headroom for Astro’s `2000px` lightbox derivative

The six representative inputs totalled `9,100,997` bytes. The selected `2560px/88` setting produced `1,762,840` stored bytes and `1,092,740` bytes after an Astro-equivalent `2000px/86` second pass. `2560px/90` increased stored size to `1,999,252` bytes without a visible benefit in the reviewed contact sheets; `2400px/85` reduced stored size to `1,402,982` bytes but provided less source headroom. Aggregate decoded comparison against direct source-to-`2000px/86` output was `37.83 dB` PSNR for the selected setting.

The complete ordered Goodies 2025 batch then converted `14` inputs (`4,372,533` bytes) into `14` WebP review outputs (`2,521,672` bytes).

### Temporary discard workflow

The first implementation should not offer a broad automatic delete flag.

Safe sequence:

1. read originals from the user-provided batch
2. write WebP results to a separate review directory
3. validate counts, dimensions, hashes, and visual samples
4. publish only WebP files
5. verify content and production build
6. discard the temporary ingest copy after explicit confirmation

No permanent original archive is created.

## Phase 5 — Two-Step Routine Editorial Workflow

Purpose:

- make new batches repeatable without prematurely building a custom Decap uploader

Proposed editor flow:

1. place JPEG/PNG files in a temporary input folder
2. run the converter
3. review the WebP outputs and conversion report
4. upload only WebP files through the CMS media workflow
5. create or edit the post/standalone gallery
6. enter or review alt text and optional captions
7. save and publish
8. verify the deployed gallery
9. discard the temporary originals

Work:

- test whether the current Decap media interface accepts practical multi-file selection for this gallery workflow
- document the exact editor interaction observed, not assumed
- ensure WebP is accepted in image fields and previews
- add concise CMS hints stating that publication uploads must be prepared WebP files
- document recovery from partial upload or failed publication
- document filename and ordering behavior

Exit criteria:

- a non-developer can complete one test gallery from prepared WebP files
- no JPEG enters the commit
- gallery ordering and alt text survive CMS save/reload
- the process is short enough to use routinely

## Alternatives Considered

### Re-scrape Goodies 4 Tricks 2025

Decision: rejected.

Reason:

- all fourteen gallery sources are already locally retained
- re-scraping adds network dependence and duplicate evidence without filling a gap

### Treat current migrated gallery counts as source truth

Decision: rejected.

Reason:

- Goodies 2025 proves migrated content can be an editorial subset
- implementation presence does not establish source completeness

### Automatically expose every post with a gallery

Decision: rejected.

Reason:

- it bypasses the media collection’s established responsibility to control media-page inclusion
- not every article gallery necessarily belongs on the media landing page

### Add `showOnMediaPage` to posts

Decision: rejected in favor of media-index references.

Reason:

- it moves media-page curation into the post model
- a media entry referencing a post preserves explicit page indexing without duplicating gallery data

### Duplicate complete post galleries into media frontmatter

Decision: rejected.

Reason:

- image order, alt text, captions, and later corrections would have two owners

### Astro build-time conversion only

Decision: rejected as the ingest solution.

Reason:

- it protects visitors but commits the original JPEG to Git first

### CI conversion after CMS publication

Decision: rejected.

Reason:

- the JPEG is already present in Git history
- a later deletion does not recover repository growth
- it introduces noisy conversion commits and race conditions

### Retain all new originals in Git

Decision: rejected by user preference.

Reason:

- repository growth is the problem being solved

### Archive all new originals externally

Decision: rejected by user preference.

Reason:

- the user chose discard after successful conversion rather than a NAS/original archive workflow

### Custom Decap browser conversion immediately

Decision: deferred.

Reason:

- it provides the best eventual UX but adds custom React/media-backend integration before conversion settings and editorial ergonomics are proven

### Server-side conversion endpoint

Decision: rejected for the initial workflow.

Reason:

- authentication, payload limits, temporary storage, retries, and operational maintenance are disproportionate for the current site

### Cloudinary or Uploadcare

Decision: rejected for the current architecture.

Reason:

- vendor dependency, external account/asset ownership, cost uncertainty, and CDN coupling are unnecessary while a local static workflow remains practical

### ImageMagick as the canonical converter

Decision: not selected for the repository workflow.

Current machine evidence:

- ImageMagick is installed
- `cwebp` is not installed
- FFmpeg is installed

Reason:

- relying on a machine-global binary weakens portability and output consistency
- ImageMagick may still be used for an exploratory comparison, but the maintained command should declare its runtime dependency

### Use Astro’s transitive `sharp` implicitly

Decision: rejected.

Reason:

- `sharp` is currently an optional transitive dependency of Astro
- production code must not depend on an undeclared transitive package

### Git LFS or history rewriting

Decision: rejected from this plan.

Reason:

- neither is needed to prevent future JPEG growth
- history rewriting is destructive and affects publication/reconciliation
- LFS changes Netlify/Decap asset behavior and does not replace a conversion policy

### Immediate staging/archive cleanup

Decision: rejected.

Reason:

- asset policy forbids using current references as a proxy for future need
- gallery completeness and final asset curation must be settled first

## Risks And Controls

### Lossy conversion quality

Control:

- benchmark representative inputs and final Astro derivatives before locking quality

### Double WebP encoding

Control:

- inspect final build output, not only stored publication files
- keep enough source quality and dimension headroom for the bounded lightbox derivative

### EXIF orientation errors

Control:

- auto-orient before resizing and add portrait test fixtures

### Metadata/privacy leakage

Control:

- strip unnecessary EXIF and location metadata from publication assets

### Browser/CMS batch limitations

Control:

- verify the actual Decap upload workflow in Phase 5; do not claim batch support from assumption

### Duplicate names and ordering loss

Control:

- stable slug-and-index naming, collision checks, and a conversion manifest

### Accidental source deletion

Control:

- separate output directory, no default delete flag, explicit post-validation discard step

### Missing historical images

Control:

- source-ID inventory and live fallback only where retained evidence is incomplete

### Duplicate content ownership

Control:

- media reference points to canonical post gallery; standalone gallery owns its own structured items

### Git remains historically large

Control:

- report honestly that future conversion stops new growth but does not erase existing blobs
- treat any later history cleanup as a separate explicitly approved operation

## Remaining Questions

1. Which historical galleries, beyond the explicitly selected Goodies 2025 restoration, should later be restored or indexed on `/pics-n-vids/`?
2. What WebP quality and maximum dimension survive the representative benchmark?
3. Does the current Decap interface provide an acceptable practical batch-selection flow for prepared WebP files?
4. Are optional visible captions desired for historical galleries, or should restoration normally use alt text only unless captions already exist in source evidence?

Existing Wix raw evidence remains preserved and outside the deletion scope of this implementation. The discard decision applies to new temporary ingest inputs after successful conversion and validation.
